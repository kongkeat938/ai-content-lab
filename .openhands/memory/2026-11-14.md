# 2026-11-14 (Sat) — Session 6

## PCSEV: `videos.update` erased description + tags on every retitle

**Problem.** `scripts/audit_channels.py --slug genx` reported Shorts with NO tags and a
few with NO description; one clip was named as "removed".

**Cause (measured).** `scripts/optimize_titles.apply_title()` built
`videos.update body={"snippet":{"title","categoryId"}}`. YouTube `videos.update` REPLACES
the whole `snippet` part — a field left out is ERASED, not preserved. So every title change
wiped `description` (which holds the subscribe ask + the tail link) and `tags`.
Measured live (Data API): genx 146 uploads, **123 with no tags (84 %), 5 with no description**;
**120 of the 123 no-tag clips were in `docs/title_changes.json`** (correlation 97.6 %). Raw
snippet for `dnCaDuZ--R0` had **no `tags` key at all** — consistent with a full replace.
`polish-all.yml` runs `optimize_titles --all --apply` for every channel, so the leak was
fleet-wide and growing. A second writer, `scripts/apply_packaging.set_title_tags`, did the
same to the description. `optimize_seo.py` (the one script that sets desc+tags) has NO caller
— it was written to fix this and never wired in.

**Solution + Execute (done).**
1. `optimize_titles.apply_title` now reads the current snippet and writes
   title + description + tags + categoryId + languages back (read-merge-write).
2. `apply_packaging.set_title_tags` likewise; its `snippet()` fetch now also pulls
   description + languages.
3. New guard `scripts/test_snippet_update_preserves.py` — runs the real `apply_title`
   against a fake network and asserts the PUT keeps description/tags/language; a source
   scan fails any other `videos part=snippet` write whose body omits them. Proven to FAIL
   when either fix is reverted.
4. New rail `scripts/restore_metadata.py` + `.github/workflows/restore-metadata.yml`:
   rebuilds description+tags from the manifests (`content/<ch>_shorts/scripts.json` +
   channel tail; `content/<ch>_publish.json` for long-form), touches only clips MISSING
   them (idempotent), stops cleanly on `quotaExceeded`, ledger `docs/metadata_restore.json`.
   Wired into `foreman.py` (daily 08–12 UTC) + `health.py` (`restore-metadata: 1700`).
5. `polish-all.yml` keeps `--apply` (safe again) with a comment pointing at the guard.

**Verify.**
- `test_snippet_update_preserves.py` → OK on fixed code; exits 1 on each reverted bug (both
  proven). Full suite **PASS=65 FAIL=0**.
- Live damage confirmed by the Data API (above). The live RESTORE cannot run now: the Data
  API read quota is spent (403 "exceeded your quota", measured 15:00 UTC) — it runs on the
  daily rail after the 08:00 UTC reset. **Honest status: fix landed + guarded; the 123 clips
  are restored by the rail over the next runs, not yet done.**
