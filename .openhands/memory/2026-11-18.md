
## Shorts loudness overshoot (K: "ทำคลิปให้ได้มาตรฐานสม่ำเสมอ")
- **Symptom (live):** publish-shorts run 44238652405 — ch4 Short #118 HELD by the gate:
  "loudness -12.3 LUFS is off the -14.0 target". The gate was RIGHT; the builder was wrong.
- **Cause (measured, reproduced):** `make_short.normalise()` applied a **fixed +2 dB**
  (`BED_GAIN_DB`) after loudnorm on the bed path. That +2 was added 2026-11-07 when `bed_gain()`
  was a fixed 0.18 that left the mix far below target. On 2026-11-09 `bed_gain()` changed to put
  the bed ~11 LU under the voice, so the mix already sits at voice level and loudnorm reaches -14
  on its own — the +2 then double-counted. Reproduced: bed path **-12.8** vs no-bed **-14.1**.
  Swept voice levels (-12/-18/-24 dB) + a loud bed: bed path -12.8…-12.9 every time.
- **Fix:** drop the fixed +2 (delete `BED_GAIN_DB`); `normalise()` now pins the finished file by
  measurement with a **SECOND loudnorm pass** (not a raw volume gain — that broke true peak:
  volume+alimiter → -2.4 dBTP, over the -3 ceiling; 2nd loudnorm → -14.9/-2.9, both in tolerance).
  Only corrects when |I-(-14)|>0.3.
- **Verify:** new `scripts/test_short_loudness.py` (fail-able; builds a REAL ffmpeg mix and runs
  the REAL upload gate) — bed path now passes. Suite **94/94**. A real `make_short.py` build
  measured -14.5→-15.0 LUFS / -3.0 dBTP → gate PASS.
- **Note:** `remake_shorts.py` reuses `make_short.py`, so the fix covers remakes too.

## Duplicate long-form title (a measured YPP trap)
- **Symptom (live):** `check_duplicates --slug dharma` found **2 dharma LONG-FORM videos with the
  identical title** `ธรรมะก่อนนอน ปล่อยวางความเครียด จิตสงบ หลับสบาย` (`lKt_A63IUmg` 125m,
  `4EzAMP7urS4` 131m). Two videos compete for one query + a "repetitious content" signal.
- **Cause (measured):** `optimize_titles.py` proposes **one title at a time** with no view of the
  channel's other titles. The ledger `docs/title_changes.json` proves it: two separate runs
  (2026-11-14 and 2026-11-17) both got the same LLM title for two similar clips.

  proposal equal to a sibling's live title as a collision (never collides with its own);
  `best_title(avoid=...)` names the live titles in the prompt; the loop re-asks once then **skips**
  rather than shipping a dup. Guard `scripts/test_optimize_titles_dedup.py` (mutation-tested FAIL).

## Thumbnail `--skip-existing` false pass (a truthy URL is not proof)
- **Symptom:** `set_thumbnails.py --check` said every dharma thumbnail was "custom"; `--skip-existing`
  would skip all 13 forever. But the manifest file for `DHs1j6o0JE0` was NOT what YouTube served.
- **Cause (measured):** `current_thumbnail()` returned a `maxresdefault.jpg` URL and the code treated
  any truthy URL as "custom set". YouTube publishes `maxresdefault` for an **auto-generated frame**
  too. Content compare (corr of served frame vs our file): the other 12 = **+0.999 (ours)**,
  `DHs1j6o0JE0` = **+0.432 (auto frame)**.
- **Fix:** `matches_live()` downloads what YouTube serves and correlates it with the file we meant to
  install (>0.9 = ours); any error = False (an unknown is never "done"). `--skip-existing` + `--check`
  use it. Guard `scripts/test_thumbnail_skip_existing.py` runs the REAL compare on REAL images;
  mutation-tested FAIL.
- **Execute/Verify (partial, honest):** re-ran `thumbnails.set` for `DHs1j6o0JE0` → API **HTTP 200**.
  The live frame then showed the marker image I set on one CDN host (`i.ytimg.com`) while
  `img.youtube.com` served an older copy — **CDN propagation lag** (`max-age=300`, and this video is a
  73s **Short**). So the set DOES apply; it is not an API failure. `matches_live()` correctly keeps
  saying `False` until the CDN converges — it will not false-pass. **Open:** confirm the live frame
  equals our file once the CDN settles (background poll).
