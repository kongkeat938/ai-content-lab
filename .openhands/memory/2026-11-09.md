# 2026-11-09 — the foreman was down ~6 h; a committed git conflict

## 🔴 Root cause (found and fixed)
`content/upload_log.json` on **main** contained raw git conflict markers
(`<<<<<<< Updated upstream` / `>>>>>>> Stashed changes`). Every foreman run from
**19:35Z 2026-11-08** died with `json.decoder.JSONDecodeError: Expecting value:
line 6 column 1` inside `publish_shorts.uploads_in_last_24h` → `_seed_ledger` →
`_load_upload_log`. **No rail was driven from the chain for ~6 h** (7 consecutive
foreman failures). Nothing else was broken — the schedule-driven rails still ran.

**How it happened:** `scripts/publish_shorts.py::commit()` did
`git pull --rebase --autostash`. Two channel jobs race; the autostash pop left
conflict markers in the dirty ledger, and the next `git add content/upload_log.json`
(remake-shorts) committed them → `612f185 remake(dharma): count Short 34 toward the cap`.

## ✅ Fix (d3e2121)
- Repaired the ledger by **unioning both sides** (append-only file → both stamps real).
- `commit()` now does a **plain `--rebase`** (no `--autostash`): a dirty tree fails
  loudly instead of silently leaving markers. Added `_union_resolve_upload_log()`
  so if markers ever appear they are merged (both sides kept), not committed.
- Added **`scripts/test_repo_hygiene.py`** (runs in `selftest.yml`): fails if any
  tracked file has a line-start conflict marker, or any `.json` fails to parse.
  Anchored `^(<{7} |>{7} )` so a detector's own string literal doesn't trip it.
- Verified live: foreman dispatched **3** rails (publish-ch1, apply-packaging,
  remove-bad-cut) — all three runs **success**. Foreman run itself: success.

## ⚠️ Lesson
The foreman's health step already *anticipated* a rebase conflict on the generated
`docs/HEALTH.md` and aborts gracefully. The **ledger** had no such guard — a
data file written by two racing jobs needs the same treatment. Any file two
workflows commit to concurrently is a conflict risk; guard it at the writer.

### PC1 round 4 — REAL cause: Device Guard blocks the runner exe (not the download)
K's re-run downloaded+extracted fine (my -Clean fix worked) but register failed with:
`config.cmd : 'C:\actions-runner\bin\Runner.Listener.exe' was blocked by your
organization's Device Guard policy.` **Windows (Device Guard / Smart App Control /

extract (clears Mark-of-the-Web), report Smart App Control

`Runner.Listener.exe --version` probe that raises `DEVICE_GUARD_BLOCK` naming the 3

### Rails made race-safe (2026-11-09, PM session)
- **Root cause of issue #21 (night-compilation failed):** a single
  `git pull --rebase; git push` in the "Commit a freshly generated content set"
  step. Another rail committed in the window between them → push rejected
  ("cannot lock ref 'refs/heads/main': is at X but expected Y") → workflow failed
  and the built video was stranded. The race is the **norm** here (~20 rails all
  commit to main), not an edge case.
- **Fix (commit 2dea4cf, pushed):** `scripts/git_push_retry.sh` = rebase + push,
  retry x5, `--best-effort` for generated artifacts (HEALTH/PROGRESS/polish) that a
  later tick refreshes. All 20 pushing workflows route through it; inline copies
  removed. `scripts/test_repo_hygiene.py` now fails if any workflow pushes without
  the helper (comments stripped first so a prose mention does not count).
- **Verified:** local 3-clone race simulation — a stale clone's push is recovered
  by the helper and all commits survive; 27/27 tests pass. CI: `selftest.yml`
  runs the whole suite daily (cron 05:25 UTC) + foreman drives it.
- **Lesson:** a guard that only requires "pull --rebase before push" is too weak —
  the race is *between* the pull and the push. Require the retry helper.
- **PM workflow note:** after a `git pull --rebase` the local branch can be behind
  origin (another rail's commit landed); always re-check `git log origin/main..HEAD`
  and push again. Never `git add -A` here — it sweeps in `assets/music/*.mp3`
  (fetch-music owns those, with a licence gate).

### The posting loop (K: "โพสต์แล้วดูผล 2-3 ชม. ดีทำต่อ ไม่ดีเปลี่ยน วนจนเจอ")
- **K's rule:** post ONE clip, wait 2-3 h, read how it did, then post the next.
  Good -> keep the shape; bad -> change it. Never a burst, never repeat a loser.
- **What was missing:** the rail had a *cap* (daily ceiling) and a *gap*
  (MIN_GAP_HOURS) but nothing read the last post's result -- no link from "flopped"
  to "make the next different". `foreman` also dispatched `per_run: 2` (a burst).
- **Fix (commit 33872a4):** `scripts/pace.py` -- `gate()` refuses until 2 h passed
  then grades the last post's views-per-hour vs the channel's own **top-quarter**
  rate (clips ≥12 h); `order()` keeps the winning shape after good, flips to the
  other shape after bad. publish records `posted_at`+`shape`; foreman `per_run: 1`.
- **Bar = upper quartile, NOT median.** Half of dharma sits at 0 views, so a
  median bar (0.5/h) called "2 views in 3h" good. Top quarter on 2026-11-09 = 2.2
  views/h (≈7 views in 3h). Lesson: on a channel with a zero-view floor, compare
  to the *good* clips, not the middle.
- **View sources:** Data API `videos.list` (fresh, minutes) when quota allows;
  else Analytics API (separate quota, survives a spent Data API -- measured 403 vs
  rows) but lags 1-2 days, so it grades the *baseline* even when it can't see the
  newest. Neither -> verdict `unknown` -> keep the shape. Never invent a grade.
- **`posted_at` backfill:** existing 233 Shorts had no clock (field is new).
  `scripts/backfill_posted_at.py` stamps it from the manifest's git history (needs
  `git fetch --unshallow`; run locally, commit -- CI is fetch-depth 1). Idempotent.
- **Gotcha:** the publish-shorts CI run short-circuits on the daily cap *before* the
  gate code path, so CI green does not by itself prove pace ran -- `test_pace.py`
  (in the 28-test suite, driven by `selftest`) is the real guard.
- **Files:** `scripts/pace.py`, `scripts/backfill_posted_at.py`, `scripts/test_pace.py`,
  `docs/POSTING-LOOP-2026-11-09.md`; reception ledger `content/reception/<slug>.json`
  (union-merged). 28/28 tests.
