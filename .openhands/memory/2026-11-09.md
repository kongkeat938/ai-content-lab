# 2026-11-09 — the foreman was down ~6 h; a committed git conflict

## 🔴 Root cause (found and fixed)
`content/upload_log.json` on **main** contained raw git conflict markers
(`<<<<<<< Updated upstream` / `>>>>>>> Stashed changes`). Every foreman run from
**19:35Z 2026-11-08** died with `json.decoder.JSONDecodeError: Expecting value:
line 6 column 1` inside `publish_shorts.uploads_in_last_24h` → `_seed_ledger` →
`_load_upload_log`. **No rail was driven from the chain for ~6 h** (7 consecutive
foreman failures). Nothing else was broken — the schedule-driven rails still ran.

**How it happened:** `scripts/publish_shorts.py::commit()` did
`git pull --rebase --autostash`. Two channel jobs race; the autostash pop left
conflict markers in the dirty ledger, and the next `git add content/upload_log.json`
(remake-shorts) committed them → `612f185 remake(dharma): count Short 34 toward the cap`.

## ✅ Fix (d3e2121)
- Repaired the ledger by **unioning both sides** (append-only file → both stamps real).
- `commit()` now does a **plain `--rebase`** (no `--autostash`): a dirty tree fails
  loudly instead of silently leaving markers. Added `_union_resolve_upload_log()`
  so if markers ever appear they are merged (both sides kept), not committed.
- Added **`scripts/test_repo_hygiene.py`** (runs in `selftest.yml`): fails if any
  tracked file has a line-start conflict marker, or any `.json` fails to parse.
  Anchored `^(<{7} |>{7} )` so a detector's own string literal doesn't trip it.
- Verified live: foreman dispatched **3** rails (publish-ch1, apply-packaging,
  remove-bad-cut) — all three runs **success**. Foreman run itself: success.

## ⚠️ Lesson
The foreman's health step already *anticipated* a rebase conflict on the generated
`docs/HEALTH.md` and aborts gracefully. The **ledger** had no such guard — a
data file written by two racing jobs needs the same treatment. Any file two
workflows commit to concurrently is a conflict risk; guard it at the writer.

## 🟠 The tracking system was lying — 3 defects found and fixed (03:00Z)

After the foreman recovery the rails were all green, so I audited the *watching*
instead of the work. Three real defects, all in the tracking/learning layer:

### 1. The learning loop was blind whenever the Data API quota was spent
`studio_ai.py` and its twin `video_review.py` read the Analytics API (own quota,
so it works) and then fetch titles from the Data API `videos.list`, which **403s
most days here**. The code fell back to the literal `"(title unavailable)"`.

Measured in the 01:12Z studio-ai run: **every winner on all three channels was
`"(title unavailable)"`**, so the panel was asked to judge a channel it could not
see. It answered with generic filler ("3 ข้อห้ามทำสิ่งนี้ถ้าไม่อยากพลาด",
"เคล็ดลับลับที่ 90% ของคนยังไม่รู้") and `gen_short_scripts.py` picked those up as
the next content to make. The "learning brain" learned from nothing.

**Fix.** New `manifest_titles()` reads the committed `content/<ch>_shorts.json` and
`content/<ch>_publish.json` (title we uploaded, offline, no quota). Live title still
wins. Pure `fill_titles()` so a test can prove the quota-spent path.
**Guard:** `scripts/test_learning_titles.py` — 74/104/49 videos keep real titles.

### 2. The health alert cried wolf on a healthy chain
`health.EXPECTED["foreman"]` was **90 min**, but the watchdog chain ticks the
foreman **every 2 h** → every healthy link tripped the alert. `set-thumbnails` was
**90 min** while the foreman only dispatches it past a **180-min** gate → its
threshold was unsatisfiable. Result: issues #7–#18 (11 of them) opened and closed
in ~30 s each over two days. **Fix:** thresholds set against the REAL driver —
`foreman` 240, `set-thumbnails` 240.

### 3. Six foreman-driven rails were invisible to health
`health.py` watched 17 workflows; six the foreman dispatches (`studio-ai`,
`selftest`, `counter-ledger`, `ch2-playlists`, `fetch music`, `short doors`) were
not in `EXPECTED`. **One was already dead:** `fetch music` had been failing for a
day — run 42475996215, `ModuleNotFoundError: No module named 'numpy'`, because its
validator imports `test_music_beds.py` and the workflow installed ffmpeg but not
`requirements.txt`. health.py still printed "all rails fresh".

**Fix.** `fetch-music.yml` installs `requirements.txt`. The six rails are added to
`health.EXPECTED` (condition-gated rails — `remake shorts`, `apply-packaging`,
`remove-bad-cut` — are deliberately exempt). The runs lookup now resolves the
workflow by **numeric id** from the workflow list: addressing by `<name>.yml`
breaks whenever the display name differs from the file name (`"fetch music"` vs
`fetch-music.yml`), and that 404 used to blank the whole report via `_error`.

**Guards added** to `scripts/test_watchdog.py` (runs in the foreman job every tick):
- every health threshold must sit above the real driver cadence;
- every foreman-dispatched rail must be watched by `health.py` (or be on the
  condition-gated exemption list).
Both were verified to **fail** when the fix is reverted. All 16 guard tests pass.
