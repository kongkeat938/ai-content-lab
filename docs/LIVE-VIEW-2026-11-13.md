# Browser Live View — a lighter way in than VNC (2026-11-13)

K asked whether anything beats VNC for watching/controlling the agent's browser. Answer:
yes — **a CDP Browser Live View**, and it is now shipped and measured.

## What it is

`scripts/browser_live.py` serves the agent's Chromium **tab** to a normal web page:

* out: `Page.startScreencast` streams JPEG frames of the tab over one websocket;
* in: clicks, wheel and keys the human sends go back as `Input.dispatchMouseEvent` /
  `Input.dispatchKeyEvent` on the same channel.

No X server, no RFB, no desktop — only the tab. It listens on **port 12000 (work-1)**.

    scripts/browser_live.py --port 12000     # or: scripts/start_novnc.sh (starts both)

Open `$WORK_HOST_1/`. VNC stays on **port 12001 (work-2)** as the fallback.

## Advisor panel (4/5, `scripts/advise.py`)

Ranking for a **recycled, non-root, no-GPU pod**: **CDP live view (1) > VNC (2) > Xpra (3)
> Guacamole (4) > WebRTC/Neko/Selkies (5)**. Reasons: the live view reuses what is already
running (CDP :9222) and encodes only the tab; WebRTC/Guacamole/Xpra need installs that a
non-root ephemeral pod cannot keep. All four said **keep VNC as a fallback**, not replace it.

## Honest limits (why VNC is kept)

* **OS-level dialogs are invisible to the live view.** A native file picker, a Chrome
  extension popup, or an HTTP basic-auth prompt is outside the tab, so `startScreencast`
  never shows it. Use noVNC for those.
* **High motion can spike CPU.** `startScreencast` encodes on every change; `everyNthFrame`
  and `quality` cap that (defaults here: quality 70, everyNthFrame 1).
* **Disconnect handling** must re-`attach`; the server stops the screencast and closes
  cleanly on client loss.

## Not done (and why)

* WebRTC (Selkies/Neko), Guacamole, Xpra: **not installed**, need root/GPU, and would not
  survive a pod recycle — the panel ranked them last for exactly this environment.
