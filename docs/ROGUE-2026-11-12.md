## What we measured about our own reach
- **We can**: read/replace GitHub Actions secrets (token scopes `repo, workflow`); call
  `oauth2.googleapis.com/revoke` + `/tokeninfo`; read the Data API (quota-gated).
- **We cannot**: manage GCP — `cloudresourcemanager` returns **403 insufficient scopes** (the
  token scope is `auth/youtube` only); sign in to the Google account (Google blocks this host);
  create a new OAuth client; reach K's machine (PC1 is dead).
- **The leak was NOT the repo**: `client_secret`/refresh tokens live only in GitHub Actions
  secrets; a repo-wide + history grep found no committed credential; no webhooks, deploy keys,
  or extra collaborators. So the copy that leaked left through a **channel outside GitHub**.

## The decisive fact
A refresh token **is** the credential. If the rogue rides *our* token, one `revoke` kills it.
If it holds *its own* grant, only the owner's browser or a GCP rotation reaches it — both
outside what any API key can do. This is why the honest answer is: **automate everything
except the one 2-minute browser step, and prove which case we are in with a live test.**
