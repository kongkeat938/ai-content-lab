# STATUS 2026-11-09 — the tracking system was lying in two ways

Task **yt938-2**. Follow-on from the 01:42Z foreman recovery (`docs/HEALTH.md`,
`.openhands/memory/2026-11-09.md`). The rails were all green again; the *watching*
was the problem. Three real defects, all in the tracking/learning layer, found by
reading the live ledgers and run history — not by trusting the reports.

## 1. The learning loop was blind on a spent Data API quota

`studio_ai.py` (and its twin `video_review.py`) read the Analytics API — its own
quota, so it works — then fetch titles from the Data API's `videos.list`. That
call **403s whenever the shared Data API quota is spent, which is most days here**.
The code fell back to the literal string `"(title unavailable)"`.

Measured in the 01:12Z studio-ai run: **every winner on all three channels was
`"(title unavailable)"`**, so the panel was asked to judge a channel it could not
see. It answered with generic filler ("3 ข้อห้ามทำสิ่งนี้ถ้าไม่อยากพลาด", "เคล็ดลับลับ
ที่ 90% ของคนยังไม่รู้"), and `gen_short_scripts.py` picked those up as the next
content to make. The "learning brain" was learning from nothing.

**Fix.** Titles now resolve from the **committed manifests** (`content/<ch>_shorts.json`
+ `content/<ch>_publish.json`) when the API cannot answer — the title we uploaded,
offline, no quota. The live title still wins when it is available. Pure helper
`fill_titles()` so the test can prove the quota-spent path offline.

**Guard:** `scripts/test_learning_titles.py` — with no live titles, every uploaded
video on ch1/ch2/ch4 must still come back with its real title. (74 / 104 / 49 videos.)

## 2. The health alert cried wolf on a healthy chain (11 issues in 2 days)

`scripts/health.py --alert` opens a GitHub issue when a rail looks quiet and closes
it when all are fresh. The threshold for `foreman` was **90 min**, but the watchdog
chain ticks the foreman **every 2 h** — so a perfectly healthy chain tripped the
alert on *every link*. `set-thumbnails` was **90 min** while the foreman only
dispatches it past a **180-min** gate, so it could never satisfy its own threshold.

Measured: issues #7–#18 opened and closed in ~30 s each, all false alarms. A channel
trained to ignore its own alert is worse than no alert.

**Fix.** Thresholds are set against the rail's **real driver**, not its nominal cron:
`foreman` 240 min (one dropped tick allowed), `set-thumbnails` 240 min (above the
180-min gate).

## 3. Six rails the foreman drives were invisible to health

`health.py` only watched 17 workflows. Six that the foreman dispatches —
`studio-ai`, `selftest`, `counter-ledger`, `ch2-playlists`, `fetch music`,
`short doors` — were not in `EXPECTED`, so they could fail with **nobody told**.
And one already had: **`fetch music` had been failing for a day** (run
42475996215, `ModuleNotFoundError: No module named 'numpy'` — its validator imports
`test_music_beds.py`, and the workflow installed ffmpeg but not the repo's
requirements). health.py still said "all rails fresh".

**Fix.**
- `fetch-music.yml` installs `requirements.txt` before running the fetcher.
- The six rails are added to `health.py` (condition-gated rails like `remake shorts`
  and `apply-packaging` are deliberately exempt — a fixed age on a rail that is idle
  by design is itself a false alarm).
- The workflow→runs lookup is now by **numeric workflow id**, resolved from the
  workflow list — addressing by `<name>.yml` breaks on any rail whose display name
  differs from its file name (`"fetch music"` vs `fetch-music.yml`), and that 404
  used to blank the whole report through the `_error` path.

## Guards added

`scripts/test_watchdog.py` gained two checks (runs in the foreman job, every tick):
- every health threshold must sit **above** the real driver cadence;
- every rail the foreman dispatches must be watched by `health.py` (or be on the
  condition-gated exemption list).

Both were verified to **fail** when the fix is reverted, so they lock the property
in. All 16 guard tests pass in the pod.

## What is *not* claimed

Whether the corrected learning loop changes viewership. That is a content question
and needs a week of Analytics, exactly as the 2026-11-08 AVD fix does. What is
claimed and proven here: the reports now describe reality, and the loop reads real
titles instead of a placeholder.

# STATUS 2026-11-09 (b) — the tracker lied a third way, and the lever disarmed itself

Follow-on to the section above, same day. Two further defects were found by reading
the live numbers, and the decision they forced was then blocked by a third defect
that had to be fixed first.

## 3. The progress report inflated YPP watch-hours up to 92×

`progress.py` compared a **channel-level** watch-hour total against YPP's 4,000-hour
bar. That bar counts **long-form only** — Shorts have a separate path (10M views /
90 days) and their watch time does **not** count. The channel total mixes both.

Measured (28 days, 2026-10-12..2026-11-09):

| channel | reported | truth (long-form) |
|---|---:|---:|
| genx | 39% of the bar | **0.4%** (1.3 h, not 120) |
| dharma | 26% | 14.5% (44.4 h) |
| kongkeat | — | 0.2% (0.5 h) |
| total | 71.7% | **15.1%** (46.2 h) |

**Fix.** `analytics.py` splits by the `creatorContentType` dimension (its real values
are lowercase **`shorts` / `videoOnDemand`**; `VIDEO`/`SHORTS` return zero rows) into
`longform_watch_hours` / `shorts_watch_hours`. `progress.py` reports the long-form
figure only, flags a pre-split sample (`lf_exact`) so a stale sample cannot masquerade
as the exact number, and adds a `retention@2min` column. `scripts/test_progress_honesty.py`
pins all of it.

## 4. The bottleneck, measured (`docs/DECISION-2026-11-09.md`)

- **The funnel is dead.** genx: 27,014 Shorts views → **2** long-form views (~0.007%).
  dharma's long-form views come from **subscribers (271)**, not Shorts (0). The playlist
  link in the Short tail does nothing.
- **The constraint is the first two minutes.** dharma's 120-min file keeps 102% at 1%
  of the file (~1.2 min), then **28.9% at 2% (~2.4 min)** — **71% leave in two minutes.**
- **Volume is not the cap** (~2.8 h/day used of a 6-8-clip capacity), and new long-forms
  are public yet get 0-7 views: a demand/funnel problem, not a publishing problem.
- The channel's winners are all **Shorts, and all specific + actionable**
  ("นอนไม่หลับ? ลองทำท่านี้ 10 วินาที"). No long-form has good retention.

**Decision:** concentrate on dharma (96% of all long-form watch time); fix the first two
minutes; steer by **long-form watch-hours/week + retention@2min**, not raw views; stop
volume long-form until retention is proven; make the Short carry a reason to click.
Review **2026-11-16**.

## 5. The lever, applied — then found disarmed

The dharma hook (`content/hooks/dharma.md`) and the night-set `open` angle now ask for a
**concrete action** (place a hand on the belly, breathe in, breathe out long) before any
reassurance. `scripts/test_hook_concrete.py` fails if either drifts back to abstraction.

Then the scheduled build revealed the lever was being **silently removed**: run
42595797071 generated `content/night_auto_202646` **missing `01_open` and `05_forgive`** —
two responses tripped the shape gate, `gen_night_scripts.py` `continue`d past them, and the
partial set was written and committed anyway. `build_night.py` globs whatever `.txt` it
finds, so the set builds a talk shorter than the arc intends and, under the `--minutes`
**floor**, is looped **twice** (the known duplicate bug). `01_open` is the exact lever the
decision names, so the silent drop disarmed the fix.

**Fix.** The generator **retries each piece three times** and, if a stage is still missing,
**raises** instead of writing a partial set. `scripts/test_night_scripts.py` proves a failing
stage aborts and writes nothing. The set was regenerated (8/8; opening now
"วางทาบลงบนท้อง", breathe in/out), the bad run cancelled, and a clean build dispatched
(run 42602924113).

## 6. The health alert cried wolf again (issue #20)

Issue #20 ("link-shorts: last success 7.9 h ago, expected <= 7.0 h") was a **false alarm** —
the same defect the earlier fix addressed, but the guard only hardcoded `foreman` +
`set-thumbnails`. `link-shorts` (gate **360** + chain **120** = 480 > EXPECTED 420) and
`set-thumbnails` (gate 180 + 120 = 300 > 240) kept firing.

**Fix.** `set-thumbnails` 240→**360**, `link-shorts` 420→**540**; `test_watchdog.py` now
**parses every `last_success_min()` gate in `foreman.py`** (19 swept) and fails if any health
threshold is not above gate + one chain tick. Verified to **fail** on the old 420 value.

## Durable rules added

1. A guard that checks "health threshold vs driver cadence" must **sweep every foreman
   gate**, never hardcode a couple of rails — a named-pair guard lets the identical bug
   live in the rest.
2. A generator that can drop a piece must **fail**, not write a partial set — a partial set
   silently changes the downstream length and triggers the loop-twice bug.
3. When a health/threshold test disagrees with the source, check for a **stale
   `__pycache__`** before believing either side.

All 19 guard tests pass. Whether retention improves is a content question and needs a week
of Analytics, exactly as the earlier AVD fix does.

# STATUS 2026-11-09 (c) — the advisor panel was one vendor and one dead slot

Follow-on to the two sections above, same day. K's standing rule is "never bring a
decision to a person — take it to ≥5 independent AI advisors". The panel was
**five slots but only two vendors** (four Gemini models on one key + Pollinations),
and one of those slots was **dead**.

## 7. A panelist name that did not exist

`advise.py` listed `gemini-latest` in `FAST`, but `ADVISORS` only defined
`gemini-flash`. The slot resolved to `"(unknown advisor)"` and the summary still
counted it as a panelist — a five-name panel that could silently be a four-model one.
**Fix:** `FAST` now names `gemini-flash`; `scripts/test_advise_panel.py` fails if any
name in `FAST`/`FAST_PLUS`/`DEEP` is missing from `ADVISORS`, and if the default panel
drops below five slots or loses a non-Gemini vendor.

## 8. A genuinely independent sixth vendor (OpenRouter, free)

Free provider scan re-run from the pod: only Gemini and Pollinations answer directly;
every keyless vendor is refused by the egress proxy. So a **keyed** free provider was
needed for real vendor diversity. K authorised using the project email + password to
sign up for free AI accounts, so an **OpenRouter** account was created and verified.

The OpenRouter UI **masks** the key value (`sk-or-v1-21a...163`) and never re-shows it,
and its internal API is Clerk-gated (a raw session cookie does not authenticate the
`/api/v1/keys` backend). The plaintext exists in exactly one place: the clipboard after
the create-key modal's copy button. So the key was created in **headless chromium**
(playwright, `/usr/bin/chromium`), logged in with email+password and the 6-digit email
code read via Gmail IMAP, and the clipboard was read out.

Measured: `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`, `cohere/north-mini-code:free`
and `nvidia/nemotron-3.5-lightning:free` all answer from the pod; Google's free slugs
(`google/gemma-4-*:free`) return upstream **HTTP 429** on the shared pool, and
`meta-llama/llama-3.3-70b-instruct:free` is **no longer free** (404 → paid slug).

**Wired in:** `ask_openrouter()` reads the key from `OPENROUTER_API_KEY` or
`~/.pod-openrouter-key`, tries the free models in order and backs off on 429/5xx.
The default panel is now `FAST_PLUS` = 4 Gemini + Pollinations + OpenRouter;
`--fast` drops OpenRouter when the free pool is busy; `--deep` still adds the three
OpenHands conversations.

**Measured run:** `python3 scripts/advise.py ...` → **6/6 advisors answered in 15.3 s**
(OpenHands deep panel is ~20 min). Evidence: `.stockwork/PANEL-EVIDENCE-2026-11-09.md`.

All 3 new panel guard checks pass. Whether more vendors change the *quality* of the
advice is a judgement question, not a measured claim.

## 12. Every rail's push is now race-safe (issue #21 fixed)

The night-compilation rail failed on 2026-11-09 (issue #21). The failed-run log
showed the cause: the "Commit a freshly generated content set" step ran a single
`git pull --rebase; git push`, another rail committed in the window *between*
those two commands, and the push was rejected — `cannot lock ref 'refs/heads/main':
is at X but expected Y` — which failed the workflow and stranded a built video.

The race is the normal case here: ~20 rails all commit to the same branch, so a
bare pull-then-push is a coin flip. The earlier guard (`test_repo_hygiene.py`)
only required "a rebase before the push", which does not cover the window between
them — measured, that guard passed on the very step that failed.

**Fix:** one helper, `scripts/git_push_retry.sh`, rebases and retries the push up
to five times (`--best-effort` for generated artifacts — HEALTH/PROGRESS/polish —
that a later tick refreshes). All 20 pushing workflows route through it; the
inline retry copies are gone. The hygiene guard now fails if any workflow pushes
without the helper (comments stripped first, so a prose mention does not count).

**Verified:** a local three-clone simulation of the race — a stale clone's push is
recovered by the helper and every commit survives (`fa`/`fb`/`fc` all present).
The full suite passes 27/27. And in CI: `polish-all` ran on the fix commit
(`2dea4cf`) and succeeded, so the edited workflow parses and the helper runs.
Issue #21 closed with this evidence.
