ในฐานะที่ปรึกษาโครงการ YouTube ไทย (`ai-content-lab`) ที่ต้องรักษากฎเหล็กของ K อย่างเคร่งครัด ขอตอบคำถามทั้ง 4 ข้อดังนี้ครับ

### 1. เลือก A/B/C หรือแบบอื่น? เพราะอะไร
**เลือก C (baseline แต่ติดป้าย unreviewed และรายงานตัวเลข)**

*   **เหตุผล:**
    *   **ไม่ใช่ A:** เพราะการปล่อยผ่านหมด (False Pass) จะขัดกับเจตนารมณ์ของ K ที่ต้องการคุมเข้มทุกบรรทัด
    *   **ไม่ใช่ B:** เพราะการบล็อกทั้งหมดทันทีจะทำให้งานหยุดชะงัก (Blocker) และการยัดเยียด 247 ไฟล์ให้ Gemini ตรวจในเวลาสั้นๆ จะทำให้ Quality ตก ซึ่ง K เกลียดงานไม่มีคุณภาพที่สุด
    *   **เลือก C:** เป็นทางสายกลางที่สมจริง (Pragmatic) ยอมรับว่ามี "เทคนิคอลเดบต์" (Technical Debt) อยู่ แต่เปิดเผยโปร่งใส (Transparency) ให้เห็นตัวเลขหนี้ชัดเจน และบังคับเฉพาะโค้ดใหม่ให้ผ่าน Gemini 100%

---

### 2. ถ้าควรเลือก C — ควรให้เห็นตัวเลขที่ไหน/บ่อยแค่ไหน ถึงจะไม่กลายเป็น "หนี้ที่ถูกลืม"
*   **สถานที่:**
    1.  **PR Comment อัตโนมัติ:** ทุกครั้งที่มีการเปิด Pull Request บอทต้องแปะสรุปสถานะ เช่น *"Repo Status: Reviewed 0/247 | Unreviewed 247"* เพื่อให้เห็นทุกครั้งที่จะ merge
    2.  **README.md (Badges):** ฝัง badge สถานะความปลอดภัย/การตรวจสอบของ Gemini ไว้ที่หน้าแรกของ Repo (เช่น `Gemini Audited: X/247 files`) ถ้าตัวเลขไม่ขยับ คนในทีมจะเห็นตลอดเวลา
*   **ความถี่:** ทุกครั้งที่มีการ Commit เข้า `main` หรือเปิด PR (Real-time update) ไม่ใช่แค่รายงานรายสัปดาห์

### 3. ควรจัดลำดับตรวจ 247 ไฟล์อย่างไรให้คุ้มที่สุด (ไฟล์ไหนก่อน)
อย่าตรวจตามตัวอักษรหรือวันที่ แต่ให้จัดลำดับตาม **"ความเสี่ยงต่อช่อง YouTube และระบบ YPP"** ดังนี้:
1.  **กลุ่มที่ 1: ระบบอัปโหลดและจัดการข้อมูลลับ (Secrets/Credentials/API Keys)** – ไฟล์ที่ยุ่งกับ YouTube Data API, Token, หรือการโพสต์วิดีโออัตโนมัติ (เสี่ยงช่องปลิวสูงสุด)
2.  **กลุ่มที่ 2: Core Scripts ที่รันบ่อยที่สุด (High-Frequency Scripts)** – สคริปต์สร้างคอนเทนต์, ตัดต่อ, หรือดึงข้อมูลที่รันทุกวัน
3.  **กลุ่มที่ 3: GitHub Actions Workflows (36 ไฟล์)** – ระบบ Automation ทั้งหมด เพราะถ้าโดนฝังโค้ดร้ายแรงใน Workflow จะอันตรายมาก
4.  **กลุ่มที่ 4: Utility / Helper Scripts ที่นานๆ ใช้ที** – ไฟล์สนับสนุนทั่วไป

*(ทยอยตรวจเป็น Batch Batch ละ 10-15 ไฟล์ต่อวัน เพื่อให้ Gemini ตรวจได้อย่างละเอียด)*

### 4. ควรกันไม่ให้ ak อนุมัติงานตัวเองได้อย่างไร (ถ้าคุณเป็นคนเขียนโค้ดเอง)
ในฐานะที่คุณ (ak) เป็นทั้งคนเขียนและคนคุมระบบ ต้องใช้หลักการ **Four-Eyes Principle (หลักการ 4 ตา)** ผ่าน GitHub Native Features:
1.  **Branch Protection Rules:** ตั้งค่าบน GitHub ว่า `main` branch ห้าม Force Push และ **"Require a pull request before merging"**
2.  **Required Approvals:** ตั้งค่าให้ต้องมีคนอื่น Approve (ถ้าทำคนเดียว ให้ใช้ **GitHub Actions บังคับ** ว่าการจะ Merge ได้ ต้องมี Comment อัตโนมัติจาก Gemini ที่มีข้อความรหัสยืนยัน เช่น `[GEMINI-APPROVED-HASH: ...]`)
3.  **Guard Script ที่คุณกำลังทำ:** เขียนเงื่อนไขใน Guard ว่า **ห้าม ak (คุณ) กด Merge เองเด็ดขาด** ถ้าไม่มีหลักฐาน (Artifact/Log) ว่าผ่านการตรวจสอบจาก Gemini API จริงๆ หรือถ้าคุณเป็นคนกด Merge ระบบจะต้อง Log ชื่อคุณคู่กับหลักฐานอนุมัติของ Gemini ไว้เป็นหลักฐานให้ K ตรวจสอบย้อนหลังได้ทันที
