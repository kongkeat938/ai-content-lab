### 3. วิธีแก้เทสต์ flake ของ `content/insights/ch4.json`
* **ห้ามพึ่งพา AI 100% ในขั้นเทสต์:** LLM มีโอกาสตอบนอกกรอบ (Flaky)

## Google — gemini-3.6-flash

ข้อสรุปเชิงยุทธศาสตร์และการแก้ไขเรียงตาม **ผลตอบแทนต่อแรง (Return-on-Effort: RoE)** เพื่อปกป้อง pipeline ของ **dharma (ch2)** ที่แบก YPP 49.4 ชม. (98.6%) และปลดล็อก **kongkeat (ch4)** จาก mid-retention 13.7% (0 วิวใน 2 วันล่าสุด):

---

### อันดับ 1 (RoE สูงสุด): แก้ Bug คีย์ + เพิ่ม Guard ใน `write_insights` (ตอบข้อ 1 และ 2)

**วิเคราะห์:** ต้นเหตุถูกต้อง 100% (`TOPICS_HINT` ใช้คีย์ `kongkeat` แต่ระบบเรียกด้วย `ch4`) 
*ทำไม push 2026-11-10 ถึงไม่แดง:* เพราะ LLM สุ่มตอบคำที่มีความตึงเฉียดผ่าน regex ในวันแรก หรือไฟล์ JSON เก่ารอดมา พอรอบ 2026-11-11T01:29Z LLM เจน 8 หัวข้อแบนเรียบ ('พ่อกอดลูกชาย 1 ปี' ฯลฯ) CI เลย FAILED ทันที (1/100 รัน)

**สิ่งที่ต้องทำ:**
1. แก้คีย์ใน `TOPICS_HINT` ให้เป็น `ch4` (ข้อ ก) และเพิ่ม Unit Test เช็คว่า `question_for('ch4')` ต้องมีคำว่า "ปมตึง" (ข้อ ค)
2. ใน `write_insights` ของ `studio_ai.py` ให้กรองทิ้งหัวข้อที่ไม่มี `_TENSION` ก่อนเขียนลงไฟล์ `ch4.json` (ข้อ ข)

> **สิ่งที่ไม่ควรทำ:** *ห้ามหวังพึ่งพากระบวนการ Prompt Engineering (`TOPICS_HINT`) เพียงอย่างเดียวโดยไม่มี Code Guard กรอกทิ้ง*
> **เพราะ:** LLM มีอัตราหลุด (hallucination/drift) 5-10% เสมอ หากหลุดไปถึงขั้นตอนผลิตคลิป Hook จะแบน ส่งผลให้ retention ตกไปที่ 13.7% และโดน YouTube feed ตัดมองเห็นเหลือ 0 วิวเหมือนเดิม

---

### อันดับ 2 (RoE ปานกลาง): ปรับ Test Guard ให้ Deterministic (ตอบข้อ 3)

**วิเคราะห์:** การวัดผลความตึงต้องการันตีที่ชั้นของ Logic ไม่ใช่ลุ้นกับผลลัพธ์สดของ LLM ใน CI

**สิ่งที่ต้องทำ:**
1. **Unit Test (Deterministic):** เทสต์ `studio_ai.py` โดย Mock ผลลัพธ์ LLM (ส่งทั้งข้อความตึงและแบนเข้าทดสอบ) เพื่อเช็คว่า `write_insights` กรอง 8 หัวข้อแบนออกได้จริงไหม
2. **Write-Time Exception:** หาก LLM เจนหัวข้อแล้วกรองเหลือ 0 หัวข้อ ให้ `write_insights` พ่น Error/Fallback ทันทีในขั้นตอนรันสคริปต์ ไม่ปล่อยให้เขียน JSON ขยะลง git repository

> **สิ่งที่ไม่ควรทำ:** *ห้ามเอาไฟล์ JSON ที่ generated จาก Live LLM มาเป็นตัวตัดสิน CI pass/fail ใน Integration Test*
> **เพราะ:** จะทำให้เกิดปัญหา Flaky CI (เดี๋ยวเขียวเดี๋ยวแดงตามอารมณ์ AI) ซึ่งรบกวนระบบอัตโนมัติ 100% บน GitHub Actions และอาจบล็อก deployment ของช่องหลักอย่าง dharma (ch2) โดยไม่จำเป็น

---

### อันดับ 3 (RoE ระยะยาว): ล้าง Schema ชื่อช่องด้วย Single Source of Truth (ตอบข้อ 4)

**วิเคราะห์:** ระบบมีความสับสนของชื่อคีย์ 3 ชุด (`ch4`, `kongkeat`, `kongkeat-story`) ทำให้เกิด Bug คีย์หลุด

**สิ่งที่ต้องทำ:**
1. สร้าง Central Mapping (เช่น `CHANNEL_MAP` ในไฟล์ config กลาง) สำหรับแปลง Identifier:
   `ch4` (Studio ID) $\leftrightarrow$ `kongkeat` (Alias/Prompt ID) $\leftrightarrow$ `kongkeat-story` (File/Repo ID)
2. ให้ทุกสคริปต์ (`studio_ai.py`, `gen_short_scripts.py`, `publish_shorts.py`) เรียกผ่าน Mapping นี้เท่านั้น

> **สิ่งที่ไม่ควรทำ:** *ห้าม Hardcode string literal ('ch4' หรือ 'kongkeat') กระจัดกระจายตามสคริปต์ต่างๆ อีกต่อไป*
> **เพราะ:** เป็นความเสี่ยงเงียบ (Silent Failure) ที่รอวันระเบิดเมื่อมีการขยายช่อง หรือเพิ่มกฎใหม่ในระบบอัตโนมัติ

### 3. ทำ how to guard against flake ของ test บนไฟล์ `content/insights/ch4.json`  

| วิธี | คำอธิบาย | Guard ว่า “ล้มได้จริง” |
|------|-----------|-----------------------|
| สร้าง **stub panel** ขึ้นใน `scripts/test_pace.py` | ไม่ใช้ panel จริง (ความหลากหลาย) | Stub ส่งหัวข้อที่มี `_TENSION` ตรง ๆ, test เข้า `TOPICS_HINT` แล้ว `question_for` เสมอได้ |
| ใช้ **regex‑check** ใน test ก่อน reading JSON | ตรวจสอบตัวแปรเส้นทางว่ามีค่า `_TENSION` ครบ 1 รายการ | ถ้าไม่มี → fail การ test ก่อนทำ parse |
| เก็บ **model/seed** ของกลับ‑ค่าผู้ใช้ panel | ระบุค่า `seed=123` ให้ได้ planning deterministic | ทำให้ test repeatable แทนการ call panel random |

**Guard ที่ “ล้มได้จริง”**:

- `assert '_TENSION' in topic` ที่ต่อเนื่องผ่านตัวแปร `TOPICS_HINT` ก่อนขั้นตอน write
- `assert len([t for t in topics if '_TENSION' in t]) > 0` ในทดสอบไฟล์ JSON
