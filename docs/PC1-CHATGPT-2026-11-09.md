## ANSWER (verified against Microsoft Learn + an expert-model consult, 2026-11-09)

Short version: the runner is a dead end under Smart App Control, and Smart App
Control is irreversible. The safe way out is a signed-PowerShell bridge, which is
now built.

1. **Which is it?** Read
   `HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy\VerifiedAndReputablePolicyState`
   (2 = On, 1 = Evaluation, 0 = Off) for Smart App Control, and
   `(Get-CimInstance Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard).UsermodeCodeIntegrityPolicyEnforcementStatus`
   (2 = enforce) for WDAC. The deciding evidence is
   **Event Viewer → Applications and Services Logs → Microsoft → Windows →
   CodeIntegrity → Operational, event ID 3077 (block) / 3076 (audit).**
2. **Smart App Control allowlist?** No. Microsoft docs: SAC has only On /
   Evaluation / Off and "unknown, unsigned code are blocked by default". There is
   no per-exe exception.
3. **WDAC:** if it is a real Code Integrity policy, it *can* be allowed
   reversibly: `New-CIPolicy -ScanFolder C:\actions-runner` →
   `ConvertFrom-CIPolicy` → `CiTool --update-policy`; undo with
   `CiTool --remove-policy <id>`.
4. **Signed runner?** No. GitHub does not code-sign the runner; Microsoft ships no
   WDAC/SAC wrapper for it.
5. **Fallback (built):** `ops/pc1_agent_bridge.ps1` — PowerShell polls a private
   repo for labeled issues and runs an allow-list; no dynamic execution, no raw
   `shell` task, token from a locked file. Guard: `scripts/test_pc1_bridge.py`.
6. **Ranking:** bridge (keeps the security posture, medium effort) > WDAC
   supplemental policy (only if WDAC, low effort, reversible) > turning SAC off
   (trivial effort, lowest security, **irreversible** — needs a Windows reinstall
   to re-enable).
