Measured 2026-11-12 (this pod): a **real (headful) Chromium on Xvfb** reaches the
Google sign-in page and is NOT turned away (title "Sign in - Google Accounts"); the
pod's **headless** browser is blocked ("browser may not be secure"). And ak can
**drive** that browser over CDP (navigate, read the page, click). So the only thing
that needs a human is the password itself — Google will not let a program type it.

3. You see a Google sign-in page already open. Type your email + password (and 2FA).
   **ak never sees the password.**
4. Leave the tab open. Tell ak "login แล้ว".

Do that for each of the three accounts (`kongkeat.938`, `farmmer.938`, `kongkeat.p3`)
— Google allows several accounts signed in at once in one browser.

## What ak does after (no K)

Over CDP on `http://localhost:9222`:
- `myaccount.google.com/brandaccounts` → the account → **Manage permissions** → invite
  the second account as **Manager** (this is the B delegation).
- The OAuth consent for the delegated token (`yt_auth.py` flow) → store it as
  `YT_<CH>_ALT_REFRESH_TOKEN`.
- Then `python3 scripts/delegate_ready.py` must print READY.

## Honest limits (measured)

- **The password is the one thing only K can supply.** ak cannot type it (Google
  detects automation) and must not be told it in chat (it would land in the log).
  The VNC screen is the safe path: K types it, ak never sees it.
- **PC1 is not a route.** `PC1_MCP_URL` is unset and PC1 is dead; the pod does this
  itself (measured above).
- If Google still challenges (2FA, "verify it's you"), K answers that one prompt in
  the same VNC screen — ak cannot.
